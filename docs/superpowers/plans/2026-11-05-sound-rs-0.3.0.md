# sound_rs 0.3.0 — professional audio library: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or
> superpowers:subagent-driven-development) to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take sound_rs from "fast Rust wrapper" to a library whose correctness, reliability
and performance claims are measured, reproducible and enforced in CI — and extend the API
where professional users actually need it (dataset loading, recording, queuing, live feeding).

**Architecture:** Keep the current shape: `src/audio.rs` owns decoding/resampling,
`src/player.rs` owns the persistent stream, `src/cli.rs` the command, `src/lib.rs` the PyO3
surface. New capability goes into the module that already owns the concern (recording is a
sibling of `player.rs`, not a new layer). Measurement lives in `bench/` and is wired into
CI; docs are generated by `docs/_build.py` from `docs/_content.py`.

**Tech Stack:** Rust 2021, PyO3 0.25, symphonia 0.5, minimp3 0.6, cpal 0.15, rubato 5,
rtrb 0.4, rayon 1.12; maturin; GitHub Actions; cargo-fuzz (dev-only); no ffmpeg, no system
decoders.

**Spec:** the scope section below is the spec; there is no separate design document. The
conversation's 0.3.0 decision (features + reliability + benchmark quality) is binding.

## Global Constraints

- Version: `0.3.0` in `Cargo.toml`; branch `release/0.3.0`; one commit per task.
- Python `>=3.10`; wheels for Linux x86_64 **and aarch64**, Windows amd64, macOS arm64
  **and x86_64** on Python 3.10–3.14.
- No new system dependencies. New crates allowed: `criterion`/`cargo-fuzz` (dev only),
  `tempfile` if a test needs a scratch dir. Nothing else without a written ruling.
- Every failure reaching Python is `sound_rs.SoundRsError` with a `.code` attribute from
  `{"io","format","device","stalled","unsupported","usage"}`; no panic may cross the FFI
  boundary.
- The GIL is released around every blocking operation (decode, playback, record, wait).
- Existing public behaviour does not change silently; any change gets a changelog line.
- Every public name in `sound_rs.pyi` appears on `docs/api.html` (`docs/check_api.py`).
- Benchmarks: every measurement in its own subprocess, warmup + ≥10 measured runs, report
  median / p95 / p99 and a 95% bootstrap CI, plus CPU time and peak RSS.
- **Release gate:** nothing is pushed, tagged, published to PyPI, or deployed to GitHub
  Pages until the human reads the report from Task 16 and says yes.

## Review Focus

The five failure modes most likely to bite a real user, each pinned by a test in the task
that owns the code:

1. Recording on a machine with no input device, or with a device that only supports 48 kHz
   stereo while the caller asked for 16 kHz mono — must raise `SoundRsError(code="device")`
   or convert correctly, never return an empty array and never hang.
2. `load(path, sample_rate=16000, mono=True)` on 1-channel, 2-channel and 6-channel files:
   shape `(frames, 1)`, duration preserved within one frame, no NaN, peak level unchanged
   within 1%.
3. `load_bytes` with truncated, empty and non-audio bytes: `SoundRsError(code="format")`
   within 5 s, no panic, no OOM.
4. `Player.enqueue` across tracks with different sample rates and channel counts, plus a
   `seek` while a queue is playing: correct per-track `duration`/`position`, no crash at the
   boundary, seek applies to the track that is playing.
5. `Player.feed()` while the ring is full and the consumer is paused, then `stop()`: the
   blocked `feed` returns within 100 ms and no deadlock is possible; underruns increment
   instead of silently dropping audio.

## Out of scope for 0.3.0 (with reasons)

- **Automatic device hot-swap** — a lost device already raises `SoundRsError(code="stalled")`
  within 2 s, which is a correct, testable contract. Reopening automatically needs a
  device-selection policy (which device to fall back to) and will be designed on its own.
- **Effect processing (gain/fade/mix)** — belongs to a mixing layer, not a playback library.
- **VST, GUI, network streaming** — separate products.
- **conda-forge** — needs its own recipe, feedstock PR and platform matrix; a separate plan.
- **A faster AAC decoder** — no drop-in candidate; documented as the slow format.
- **Windows/macOS-only features** — no platform-specific API surface in 0.3.0.
