Benchmarks

Numbers with the method next to them, including the rows where the library is slower.

Method

  • Every measurement runs in a separate process: peak RSS is process-wide, so timing and memory cannot share one.
  • Median and p95 over repeated runs; the corpus is generated by the harness so it is reproducible.
  • Correctness is checked in the same run: decoded PCM is compared with libsndfile.
  • Hardware: Apple M5 Pro, macOS 26.6.2, Python 3.14.7, release build with lto = "fat" and opt-level = 3.

Playback and memory

First soundPeak RSSOverhead
sound_rs Player, 10 min stream11.3 ms43 MB+30 ms

The playback overhead row is a 3-second tone: wall clock minus the track duration. The player number uses a stream that is already open; the one-shot play_array pays the device setup and lands around +180 ms.

Reproduce it

python bench/run.py                 # sound_rs only
python bench/run.py --compare       # + soundfile / sounddevice
python bench/run.py --reps 9

The harness generates its corpus (3 s and 10 min, WAV plus MP3/FLAC/M4A when ffmpeg is available), runs each measurement in a subprocess, and prints median, p95 and peak RSS. A full run takes about three minutes on the machine above.

Where it loses

  • MP3 alignment: 47 samples (~1 ms) earlier than libsndfile and ffmpeg. Length is exact; values match after alignment.
  • WAV decode: a memcpy race with libsndfile, 1.2× is all there is.
  • AAC decode is slower than the other formats — a newer decoder with less tuning — though libsndfile cannot decode it at all.
  • Very small files: for a 3-second tone the fixed device setup dominates everything, and all libraries land within a few tens of milliseconds of each other.
